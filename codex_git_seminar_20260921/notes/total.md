# 01_Codex、VS Code 与 Git 在科研项目中的使用

这次汇报不把 Codex、VS Code 和 Git 当作三个零散工具，而是把它们串成一条从想法到可复现结果的工作路径。Codex 负责理解任务并执行修改，VS Code 提供观察代码、终端和差异的工作区，Git 负责记录、比较与恢复。我们会先讲 Codex，再讲 Git，最后把两者组合成科研工作流。衡量这套工具链的标准不是代码产生得多快，而是研究结果是否更可靠、更容易复查。

---

# 02_ChatGPT 与 Codex 的工作方式

用同一个 MATLAB 任务看，两者的差别会更直观。如果我在普通 ChatGPT 对话中问“扩展卡尔曼滤波是什么，给一段示例代码”，通常得到的是原理说明和参考代码。接下来还要由我判断代码能否用于当前项目，把它放到合适的位置并运行验证。交给 Codex 的任务可以更具体：请它读当前工程，找到定位模块里的状态更新函数，在保持输入输出接口不变的前提下修改文件、补充测试，再说明修改了哪些文件以及测试结果。Codex 能进入授权范围内的真实项目执行这些步骤，也能查看 Git 差异。但这不等于改动自动正确，最后仍要由人检查代码和验证结果。这里的表述依据《Codex 是什么与基本使用教程》第一部分第 1、2 小节。

---

# 03_Codex 处理代码任务的基本流程

Codex 的价值不只是补出一段代码，而是围绕任务完成一个可验证的闭环。它从明确目标开始，读取项目和规则，拆解计划，修改文件，运行测试或检查，再审查差异并汇报结果。如果验证失败，就回到修改环节，而不是把未验证的代码直接交付。右侧的状态窗口强调了最终应看到的证据：测试通过、变更文件清楚，而且差异已经准备好供人审查。人在入口确认范围，在出口核对风险、证据和完成标准。

---

# 04_科研代码项目的常见目录

Codex 项目没有一种神秘或唯一的目录格式，关键是让人和工具都能迅速定位规则、实现与验证。项目根目录里，AGENTS.md 说明执行约束，README.md 提供入口，src 放实现，tests 放可重复检查。configs、data、results 和 docs 分别管理参数、数据约定、输出与方法记录。依赖文件用于锁定环境，.gitignore 则排除密钥、缓存、大型原始数据和可以重新生成的文件。目录结构的目的不是显得专业，而是让规则是什么、代码在哪、怎样运行、如何验证和结果放哪都能被快速回答。

---

# 05_项目规则与可复用技能

当项目规则稳定后，不必在每次对话里重新解释。AGENTS.md 适合记录测试命令、目录约定、提交规则、禁止事项和必要的领域背景，它回答的是这个项目始终应该怎么做。Skill 则把边界清楚、会重复出现的多步骤方法封装起来，核心是 SKILL.md，也可以配套脚本、参考资料和资源。Codex 执行任务时，一边遵守项目规则，一边在适用时调用可复用流程。接下来分别展开这两种机制，并给出可以直接迁移到科研项目中的示例。

---

# 06_AGENTS.md：项目级工作约定

AGENTS.md 可以理解为项目内长期有效的“协作说明书”，Codex 会在开始工作前读取它。全局文件适合放个人通用习惯，仓库根目录适合放整个项目的规则，更深目录中的文件则补充局部约束；从项目根目录到当前工作目录的规则会依次合并，位置越近的说明越具体。内容应优先写成可以执行和检查的规则，例如入口命令、测试方式、禁止修改的目录以及交付要求。临时任务、一次性背景和密钥不适合放进长期规则。

---

# 07_科研项目中的 AGENTS.md 示例

这份示例把科研项目中容易口头遗漏的约定写成了明确规则。它先说明 MATLAB 版本和程序入口，再要求修改前检查 Git 状态、只处理当前任务文件、不要改动原始数据，最后规定必须运行的测试和汇报内容。好的 AGENTS.md 不追求面面俱到，而是做到具体、可执行、可验证。项目成员和 Codex 因而能用同一套标准判断任务是否真正完成。

---

# 08_Skill 的结构与调用方式

Skill 是针对某一类任务的可复用工作手册，一个技能目录至少包含 SKILL.md，也可以配套脚本、参考资料和素材。Codex 通常先看到技能的名称和描述，判断任务匹配后再加载完整说明，这样既能复用专业流程，又不会把所有细节一次性塞进上下文。项目级技能可以放在 .agents/skills 下，通过美元符号加技能名显式调用，也可以依靠描述自动匹配。AGENTS.md 管整个项目的长期规则，Skill 则服务于边界清楚、会反复出现的具体任务。

---

# 09_Skill 示例：实验结果复核

这里把“实验结果复核”封装成一个最小技能。SKILL.md 用名称和描述说明什么时候使用，再规定读取配置、记录 Git 提交号、最小复现实验、比较指标和生成摘要的顺序，并明确禁止覆盖原始数据或跳过失败结果。使用时可以显式输入技能名和实验目录，也可以让 Codex 根据任务描述自动匹配。这样，同一套复核步骤能在不同实验和不同成员之间重复执行，输出也更容易比较。

---

# 10_在 VS Code 中使用 Codex

第一次在 VS Code 中使用 Codex，可以沿着三步完成。先安装或启用扩展、登录账号，并打开真实项目；然后打开 Codex 侧边栏，用目标、范围和完成标准描述任务；最后引用相关文件、选区或报错，让上下文足够精确。任务完成后，不只看一段摘要，还要检查差异和测试结果。对于真实科研项目，建议在任务前后建立 Git 检查点，这样每一次 AI 修改都有基线、有证据，也能够恢复。

---

# 11_Git 的分布式版本管理

Git 是分布式版本控制工具，而 GitHub 或 GitLab 是远程托管与协作平台，两者不能混为一谈。集中式版本控制依赖中心仓库，分布式 Git 的每个完整克隆都带有项目历史，因此即使没有网络，也能在本地提交、查看历史和比较版本。一次提交保存的是某一时刻的项目状态以及与父提交的关系，不是把整个文件夹随手复制一份。这也是 Git 能够可靠比较、分支、合并和恢复的基础。

---

# 12_Git 的四个工作位置

理解 Git 的关键，是知道文件当前位于哪一个位置。工作区是正在编辑的文件，git add 把选中的变化送到暂存区，暂存区决定本次提交包含什么。git commit 再把这批内容固化为本地仓库中的历史，只有 git push 和 git pull 才涉及远程仓库的同步。平时用 git status 看状态，用 git diff 看具体差异，用 git log 看历史。暂存区最重要的价值，是先选择这一次要提交什么，再生成一个清楚的检查点。

---

# 13_Git 的日常操作顺序

日常操作不需要记住大量命令，只要坚持一条安全循环。开始前用 git pull 同步更新，完成一个边界清楚的小修改并测试，然后用 git status 和 git diff 检查范围。接着只用 git add 暂存当前任务相关文件，用提交信息说明为什么改变，最后 git push 到对应远程分支。右侧终端示例显示了一次可解释的小提交：配置和代码变化明确，提交信息也能说明原因。没有理解影响之前，不要使用会覆盖历史或丢失修改的强制命令。

---

# 14_用 Git 管理科研实验版本

科研项目里的版本历史，应该帮助我们回答这次实验为什么与上一次不同。一个研究假设或修复可以对应一个短分支，在分支中同时修改代码和配置，验证后再合并。提交应能关联代码与配置变化、环境和数据获取说明，以及指标摘要或结果索引。源代码、配置、依赖、评估脚本和图表生成方法适合追踪；密钥、缓存、临时文件、大型原始数据和可重新生成的输出应忽略或交给专门机制管理。结果目录可以保留 README、指标摘要或索引，让提交真正指向实验记录。

---

# 15_Codex 在算法研究中能做什么

前面介绍了 Git 如何管理实验版本，现在回到科研任务本身。Codex 可以先帮助我们梳理论文的观测模型、变量和前提，再对照当前系统检查所需输入是否存在。遇到有希望的方法，先按论文条件做相对独立的最小复现，核对结果；如果对不上，再检查坐标系、归一化或评价指标等实现细节。复现之后，Codex 可以定位项目中的接口、协助接入或改造，并在相同条件下安排与基线的对照。最后，把代码、配置、运行结果和失败原因整理成可复查记录。但它不能代替研究者判断论文假设是否成立，也不能仅凭某个局部残差改善就宣布方法有效。这一页根据《科研过程复盘_Codex与Git协同工作流》的科研环节整理。

# 16_Codex 与 Git：两条算法路线的对照

最后用 Paper2 的多反射面估计说明两者怎样配合。完整全局动态规划提供一条可继续使用的基线；为了减少完整区间搜索的计算量，我们又探索粗糙度引导的受限搜索。两条路线应从明确的起始提交出发：Codex 可以在不同讨论中分别复核基线、分析瓶颈和协助实现新方案，Git 则保存基线，并用独立分支隔离探索代码。聊天分叉不会自动创建 Git 分支，需要我们明确工作目录和分支；如果要同时运行不同路线，还可以使用独立 worktree。比较时固定数据、随机种子和评价指标，重点看定位精度与计算量。是否合并新路线，或者记录失败原因后停止，由研究者根据证据决定。这是研究路线管理的例子，不表示受限搜索已经优于完整方法，也不等于相关论文均已完成严格复现。案例依据《科研过程复盘_Codex与Git协同工作流》。
